# SafeLoop 隐患管理模块设计（第一版）

## 1. 模块目标

隐患管理模块用于对 EHS 管理员确认后需要进入整改闭环的问题进行正式管理。它承接设备台账、点检记录和异常审核结果，并为整改、复查与关闭提供统一的业务对象。

第一版解决以下问题：

- 将已确认的异常转化为可追溯的正式隐患；
- 保存来源异常、关联设备和现场位置，建立从异常到隐患的追溯关系；
- 明确隐患风险等级、整改责任人和整改期限；
- 展示整改状态和期限，帮助 EHS 管理员持续跟踪；
- 为后续整改记录、EHS 复查和关闭提供基础数据。

本模块只描述内部 EHS 管理流程，不生成法规判断、合规结论或专业检验结论。

## 2. 概念边界

### 2.1 异常不等于隐患

| 概念 | 定义 | 业务边界 |
| --- | --- | --- |
| 异常 | 现场人员在点检、巡查或设备使用过程中发现的问题事实。 | 先由 EHS 审核；可以被判定为一般异常、驳回或确认形成隐患。 |
| 隐患 | 经 EHS 审核确认，需要进入正式整改闭环的问题。 | 必须有来源异常，包含责任、期限、风险等级和整改状态。 |

只有异常审核结果为“已确认隐患”时，才可以创建隐患。异常与隐患必须使用独立编号、独立状态和独立等级字段：

- 异常建议等级由发现人员提出，仅表示现场关注建议；
- 隐患等级由 EHS 管理员确认，用于整改优先级、期限和跟踪；
- 设备风险等级属于设备台账，不等同于上述两类等级。

### 2.2 基本原则

- 一条异常第一版最多创建一条隐患，避免重复闭环；
- 任何隐患必须保留来源异常编号，不允许脱离异常直接创建；
- 隐患关闭不等于删除异常，异常和隐患历史均保留只读追溯；
- 设备停用、维修中或报废不删除既有隐患，历史记录继续可查；
- 设备责任人与整改责任人可以相同，也可以由 EHS 另行指定。

## 3. 隐患来源

隐患的直接来源都是已确认隐患状态的异常记录，区别只在异常最初的发现来源。

### 3.1 点检异常来源

```text
点检任务
  ↓
点检记录 / 检查项目异常
  ↓
异常记录（待确认）
  ↓ EHS 审核确认
隐患记录
```

此类隐患应保留来源点检任务、点检记录和检查项目的可追溯关系，便于复核当时的检查事实。

### 3.2 主动上报异常来源

```text
设备责任人或现场人员主动发现
  ↓
异常记录（待确认）
  ↓ EHS 审核确认
隐患记录
```

此类隐患没有关联点检任务、点检记录或检查项目，但必须保留来源异常编号、关联设备、发现人员和现场位置。

## 4. 隐患字段设计

### 4.1 基础信息

| 字段 | 建议类型 | 业务含义 |
| --- | --- | --- |
| 隐患 ID | UUID | 内部唯一标识，用于数据关联。 |
| 隐患编号 | 文本，唯一 | 面向业务人员的可读编号，例如 `HZ-2026-001`。 |
| 来源异常 ID | 外键 | 指向 `abnormal_record`，系统关联使用。 |
| 来源异常编号 | 文本快照 | 用于页面展示和审计追溯。 |
| 来源类型 | 枚举 | 点检异常或主动上报，继承来源异常，不允许任意修改。 |
| 关联设备 | 外键 | 指向 `equipment`。 |
| 设备编号、名称、类别快照 | 文本 | 保存确认时的设备识别信息。 |
| 所在区域 | 文本 | 设备所在的较大物理区域。 |
| 具体位置 | 文本 | 设备的现场精确位置。 |
| 隐患描述 | 多行文本 | 基于来源异常和 EHS 审核形成的正式整改问题描述。 |
| 来源异常描述快照 | 多行文本 | 保留现场发现时的原始描述，避免审核描述覆盖事实。 |
| 模拟附件 | 附件关联 | 第一版仅展示模拟附件信息；未来保存受控存储路径和元数据。 |
| 创建时间、更新时间 | 日期时间 | 用于审计、排序和历史追溯。 |

### 4.2 风险与确认信息

| 字段 | 建议类型 | 业务含义 |
| --- | --- | --- |
| 隐患等级 | 低/中/高 | 由 EHS 管理员确认的正式隐患等级，不使用异常建议等级替代。 |
| 发现时间 | 日期时间 | 继承来源异常的实际发现时间。 |
| 确认时间 | 日期时间 | EHS 确认形成隐患的时间。 |
| 确认人员 | 用户关联 | 完成异常确认及隐患建立的 EHS 管理员。 |
| 确认意见 | 多行文本 | EHS 对形成隐患的审核说明。 |

### 4.3 整改信息

| 字段 | 建议类型 | 业务含义 |
| --- | --- | --- |
| 整改责任人 | 用户关联 | 对整改执行和反馈负责的人员；可与设备责任人不同。 |
| 整改期限 | 日期 | EHS 设置的整改目标日期，用于后续逾期标记。 |
| 整改措施 | 多行文本，可空 | 责任人后续提交的整改措施；创建隐患时允许为空。 |
| 当前状态 | 枚举 | 待整改、整改中、待复查、已关闭。 |
| 整改开始时间 | 日期时间，可空 | 责任人开始整改时记录。 |
| 整改提交时间 | 日期时间，可空 | 责任人提交整改记录时记录。 |
| 复查人员、复查时间 | 用户和日期时间，可空 | EHS 完成复查时记录。 |
| 复查意见 | 多行文本，可空 | 复查通过或不通过的说明。 |

## 5. 隐患状态设计

### 5.1 第一版核心状态

第一版隐患列表和详情页使用以下四个核心状态：

```text
EHS 确认隐患并完成分派
  ↓
待整改
  ↓ 责任人开始处理
整改中
  ↓ 责任人提交整改记录
待复查
  ↓ EHS 复查通过
已关闭
```

| 当前状态 | 含义 | 可转移到 | 触发角色 |
| --- | --- | --- | --- |
| 待整改 | 已明确整改责任人和期限，等待责任人开始处理。 | 整改中 | 整改责任人；第一版仅展示。 |
| 整改中 | 责任人正在执行整改。 | 待复查 | 整改责任人提交整改记录；第一版仅展示。 |
| 待复查 | 整改已提交，等待 EHS 复查。 | 已关闭 | EHS 管理员复查通过；第一版仅展示。 |
| 已关闭 | EHS 复查通过，隐患闭环完成。 | 无 | EHS 管理员。 |

责任人不能自行将隐患置为已关闭；只有 EHS 管理员复查通过后才能关闭。

### 5.2 与统一状态流转的衔接

既有状态流转文档保留“待分派”“已驳回整改”“已撤销”等扩展状态。本模块第一版不开发相应操作，处理方式如下：

- 待分派：异常确认形成隐患但尚未指定整改责任人和期限时的衔接状态；第一版模拟数据应在建立隐患时完成分派，因此列表从“待整改”开始展示。
- 已驳回整改：未来 EHS 复查不通过时使用，并返回待整改；第一版仅在后续复查模块实施时启用。
- 已撤销：未来因重复、误建或业务变化取消隐患时使用，必须记录撤销原因和操作人；第一版不开放操作。

整改逾期应作为依据整改期限计算出的时间标记，不应替代隐患主状态。

## 6. 权限设计

第一版暂不实现登录和权限控制，但页面、数据和后续 Supabase 规则应遵循以下边界。

| 角色 | 可以查看 | 可以修改 | 可以关闭 |
| --- | --- | --- | --- |
| 系统管理员 | 全部隐患、来源异常和整改状态，用于系统维护与问题排查。 | 仅技术参数、账号和权限配置；不修改隐患事实、风险等级或审核结论。 | 不关闭日常业务隐患。 |
| EHS 管理员 | 全部隐患、来源异常、设备信息和整改进展。 | 确认隐患、确定隐患等级、指定整改责任人和期限；复查并记录意见。 | 可以在复查通过后关闭隐患。 |
| 设备责任人 | 本人负责设备的隐患、来源异常和整改进展。 | 可作为整改责任人提交整改措施和整改记录；不能改写来源异常、隐患等级或期限。 | 不可以自行关闭隐患。 |
| 整改责任人 | 分配给本人的隐患、关联设备必要信息和整改期限。 | 可以更新整改措施并提交整改记录；不能修改确认意见、隐患等级或来源异常。 | 不可以自行关闭隐患。 |

设备责任人与整改责任人不是同一强制角色关系。EHS 可根据实际部门、专业能力或外部协作安排整改责任人；第一版仅使用模拟人员展示。

## 7. 第一版范围

### 7.1 第一版实现

- 使用本地虚构数据展示隐患记录；
- 隐患列表，展示来源异常、关联设备、隐患等级、整改责任人、整改期限和当前状态；
- 隐患详情，展示来源异常追溯、设备位置、确认信息、整改信息和状态；
- 整改状态展示，覆盖待整改、整改中、待复查和已关闭；
- 在设备详情、异常详情和隐患详情之间展示只读追溯入口。

### 7.2 第一版暂不实现

- 真实整改提交或状态修改；
- 真实图片上传、预览和对象存储；
- 消息提醒、超期通知和升级机制；
- 审批流、电子签名和多级复核；
- 数据库、跨页面持久化和登录权限；
- 真实复查提交、驳回整改和撤销操作；
- 自动生成隐患或自动分派整改责任人；
- AI 风险判断或法规结论生成。

## 8. 未来数据库实体与关系

### 8.1 `hazard_record`

`hazard_record` 是隐患管理模块的核心实体，保存已确认隐患、来源异常、确认信息、整改责任和当前整改状态。建议使用 UUID 主键，并以独立业务编号字段展示给用户。

| 关系对象 | 基数 | 关系说明 |
| --- | --- | --- |
| `abnormal_record` | 一对一 | 一条已确认隐患异常第一版最多对应一条隐患；隐患必须关联来源异常。 |
| `equipment` | 多对一 | 多条隐患可关联同一设备；隐患必须关联一台设备。 |
| `rectification_record` | 一对多 | 同一隐患可有多次整改记录，支持后续复查不通过后的再次整改。 |
| `review_record` | 一对多 | 同一隐患可有多次复查记录，保存复查通过或不通过的历史。 |
| `attachment` | 一对多 | 隐患确认、整改和复查可分别关联附件元数据。 |
| `operation_log` | 一对多 | 保存确认、分派、状态变化、复查和关闭等审计记录。 |

### 8.2 核心关系图

```text
abnormal_record 1 ── 0..1 hazard_record
equipment 1 ── N hazard_record
hazard_record 1 ── N rectification_record
hazard_record 1 ── N review_record
hazard_record 1 ── N attachment
hazard_record 1 ── N operation_log
```

### 8.3 数据一致性原则

- 仅当来源异常状态为“已确认隐患”时，允许创建 `hazard_record`；
- `hazard_record.source_abnormal_id` 应设置唯一约束，保证第一版一条异常最多生成一条隐患；
- 隐患创建时应保存来源异常编号、设备识别信息和位置快照，便于历史展示；
- 隐患等级、整改责任人和整改期限应在状态进入待整改前完整填写；
- 已关闭隐患不得直接修改为整改中；未来若需恢复，必须采用留痕的新流程；
- 状态转换、责任人变更和期限调整应写入操作日志；
- 附件表只保存元数据和受控存储路径，实际文件后续使用对象存储管理。

## 9. 后续开发顺序建议

1. 建立本地模拟隐患数据，覆盖四个核心整改状态和低、中、高隐患等级；
2. 建立隐患列表和详情页，优先实现来源异常、设备和整改状态的只读追溯；
3. 从异常详情的“已确认隐患”结果关联至隐患详情；
4. 建立整改记录展示与责任人提交页面；
5. 建立 EHS 复查页面，再补充驳回整改、已撤销和真实关闭逻辑；
6. 最后接入 Supabase、对象存储、行级权限和消息通知。
